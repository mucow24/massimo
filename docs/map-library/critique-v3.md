# Red-team synthesis — plan v3

## VERDICT

Yes — v3 is sound enough to implement once the five blockers land. The architecture is right and independently verified: the three-store split is arithmetically necessary (27 MB vs 1.5 MB per dialog open, and IDB offers no column projection), thumbs-on-the-revision-row correctly retires the batching problem, D4's serialize-verbatim/parse-to-load is exact, the §8 fake-indexeddb isolation snippet works and typechecks against the repo's real tsconfig, the withNeutralSelection seam extracts cleanly, and §1's ground truth is exact on ten spot-checked claims — with one load-bearing exception (§1:56's computeContentBounds gloss, blocker #1). All three v1 blockers are genuinely resolved, not hand-waved, and the v2/v3 redesign moots the rest rather than dodging it. The blockers are not architectural: two are one-line/one-paragraph spec fixes (the content gate, saveRevision's settlement contract) and three are test-plan defects that must land before red-first can mean anything (#14, #27, #38 each pass or fail against the wrong thing). The should_fix list is long but almost entirely one-line plan edits and missing assertions. Two structural cautions that the blockers don't cover: the Clear→New / empty-doc-with-live-history hole is real, pre-existing in kind, and not closable by any gate phrased over `doc` — it needs a user decision, not a patch; and ConfirmDialog is the one genuinely over-built piece, worth cutting before §9 step 4 rather than after.

**Why:** §1:56 ("Ground truth (verified)") claims computeContentBounds is "the app's own definition of 'is there anything here' — reuse it as D15's content gate", and §5.1:139 makes `if (!computeContentBounds(doc)) return; // nothing to lose` the first statement of autoSaveCurrent. D12 makes New non-undoable, dialog-free, and clearHistory()-ing; the persist store then overwrites 'vignelli-map-doc-v1' with the wiped doc. Loss is total and silent, on all three switch paths (§5.3/§5.5/§5.6). It falsifies D14 as written, and test #26 enshrines it as correct.

**Fix:** Delete the contentBounds gate and compare bytes — §5.1 already computes the string on the next line. `const EMPTY_DOC_JSON = serialize(pickDocSnapshot(DEFAULT_DOC))` at module scope; reorder to `const json = serialize(pickDocSnapshot(doc)); if (json === EMPTY_DOC_JSON) return;`. Rewrite §1:56 to state what the function is (camera hull, omits lines, 5 of 18 fields, correct for fitCameraToDoc and unfit as a data gate). Rewrite test #26 — as specified it asserts the defect; keep "truly-default doc → saveRevision NOT called" and ADD the red: "doc with two lines and no stations → New → saveRevision called with 'auto'". **Evidence:** contentBounds.ts:14-26 (camera docstring), :20-23 ("Lines are omitted deliberately"), :41-56 (five loops only), :58 (`if (!Number.isFinite(minX)) return null`). store.ts:92-119 (18 DOC_FIELDS). transforms.ts:1316 (`addLine` → `stations: []`). ### B2. §3 never says what settles saveRevision's promise — and the natural implementation resolves on a transaction that aborted, defeating D12's abort guarantee

**Why:** D12, §5.1:136 ("THROWS on storage failure — every caller MUST abort its switch") and §5.3 ("if it throws… STOP; do not wipe") all rest on saveRevision rejecting. §3:90 declares `Promise<number>` and §3:105 specifies the body ("put maps row → add revision → id → put payload → prune") but is silent on settlement. The revision id only exists at the add request's `onsuccess` (`request.result`), which is exactly where an implementer reaches for `resolve(id)` — and the transaction has not committed there. A quota/VersionError abort at the payload put or during prune then resolves with a valid-looking id, autoSaveCurrent returns normally, and New wipes a document whose revision does not exist. Tests #20/#25 mock saveRevision to reject, so they pass identically against the correct AND the broken implementation; nothing in §8 or e2e drives a real storage failure. No wrapper exists (idb/dexie absent from package.json; §4 adds only fake-indexeddb) and a repo-wide grep finds zero existing indexedDB usage, so there is no in-repo precedent to copy.

**Fix:** Add to §3, next to the sibling tx-lifetime caveat it already documents: "The returned promise resolves on `tx.oncomplete` with the id captured at the add request's onsuccess, and rejects on `tx.onabort` and `tx.onerror` (reading tx.error). It must NEVER settle on an individual request's onsuccess — the transaction has not committed there, so a quota/VersionError abort would resolve as success and defeat D12." Add a §8 mapLibrary test (the 1-13 block has no failure case): drive a real fake-indexeddb saveRevision, abort after the add succeeds, assert the promise rejects AND revisions/payloads are both empty. Keep #20/#25 (they correctly test the caller) but correct W4's "#20/#25 prove errors surface and New aborts" — they prove the caller aborts given a rejection, not that saveRevision produces one.

**Evidence:** Reproduced against real fake-indexeddb with the §2 schema built verbatim, two implementations differing only in settlement, abort injected after the add succeeds (both via tx.abort() and via a genuine ConstraintError, which is how a browser aborts on quota): resolve-at-add.onsuccess → RESOLVED id=1 with maps 0 / revisions 0 / payloads 0; resolve-at-tx.oncomplete → REJECTED. Both variants resolve id=1 with payloads 1 on the happy path. Plan §3:90, :105; §5.1:136; §8 #20/#25; §10 W4.
