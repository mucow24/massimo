# Red-team synthesis

## VERDICT

Yes — with the three blockers resolved first. The plan's design decisions are correct and its ground truth is unusually well-verified; what fails is its self-assessment. §5's core mechanism holds (zundo's undo/redo and rollback all shallow-merge, so a name-free snapshot genuinely leaves the name alone — verified against zundo 2.3.0's source), and I looked hard for a simpler alternative to the undo split and found none: pausing history inside setDocName fails because unrelated pastStates still carry the old name, and re-stamping after temporal.undo() still needs a name-ignoring equality, still needs the rollback patch, and leaves name in every snapshot as deliberately-ignored dead data. D4's serialize-verbatim / parse-to-load, §7's adoptParsedDoc extraction, §6's withNeutralSelection extraction, the meta/payload store split, and the three-store split are all right calls, and §14's self-critique is honest. But three things must land before code: the ConfirmDialog contract (unspecified, and its own test goes false-green so TDD cannot catch it), §5's inverted safety argument (R3 fears a non-risk while the real one is invisible to tsc, and #13's annotation points the implementer at a test I watched pass without the change it claims to guard), and the IDB isolation strategy (test #2 fails on test #1's leftover, and the house-style fix deadlocks the pre-pr gate at step 1). Each is a plan-text correction, not a redesign. The recurring pattern across every lens is worth naming: the plan is right about what to do and wrong about what protects it — three of its designated red tests (#13, #23, #27) pass against the bug they are named for, and two ground-truth claims used to justify new files (jsdom has no getBBox; no toast exists in src/) are false. Fix the guards, keep the design.

## BLOCKERS

### B1. ConfirmDialog's nesting, Escape ownership, portal target, and API shape are all unspecified — and test #23 goes false-green, so TDD cannot catch it

**Why:** §4 makes ConfirmDialog one shared component for three consumers; §9 nests it inside MapLibraryDialog, which itself registers `useDismiss` (Escape + backdrop) on `document`. `useDismiss` has no stack, no z-order, no topmost rule. Reproduced empirically: with a confirm open, one Escape closes BOTH the confirm and the library dialog — and it does so even when the confirm registers no dismiss logic at all, because the library's own document listener is never suspended. If the confirm portals outside `panelRef` (the plan's own pattern for every other overlay, and the likely choice since the shared confirm must also serve MapNameField inside the toolbar's z-index:1 stacking context), mousedown on the confirm's own Delete button dismisses the library dialog underneath it. Worst part: plan test #23 ('Delete map → confirm → deleteMap called, row disappears') PASSES anyway — React batches the native-listener setState while userEvent dispatches mousedown→click synchronously, so deleteMap fires and the row 'disappears' because the whole dialog unmounted. The plan's own gate cannot see this. Separately, §13 sequences ConfirmDialog at step 4 but D5's three-way rename prompt at step 7 — an implementer who builds a boolean onConfirm/onCancel API at step 4 reworks it at step 7.

**Fix:** Decide and write into §4/§9 before step 4: (1) API is a choice list, not a boolean — `ConfirmDialog<T>({title, message, choices: {value,label,danger?}[], onChoose: (v: T|null) => void})`; Clear and deletes pass two choices, the D5 rename prompt passes three. (2) Escape ownership: ConfirmDialog owns Escape exclusively; MapLibraryDialog passes `{escape: false}` to its `useDismiss` while a confirm is open (the opt exists for exactly this — usePopover.ts:25-28 — with in-repo precedent at StationInspector.tsx:113, and `escape` is in the effect dep array at :57 so toggling re-registers cleanly). (3) Outside-click: either render the confirm inside the library panel's subtree, or add the confirm's ref to the library's `useDismiss` ignore array. Do NOT rely on the `.color-field-popover` hatch at usePopover.ts:39 — it is hardcoded to that class and confers nothing on a new `.confirm-dialog`. (4) Rewrite #23 to assert all three of: confirm closed, deleteMap NOT called, library STILL open — the third is the only assertion that actually goes red.

**Evidence:** usePopover.ts:31 (`escape = opts?.escape ?? true`), :34-44 (onDocClick, no layering; `.color-field-popover` hatch at :39), :45-47 (unconditional document Escape), :25-28 (the `escape` opt's own docstring: 'two independent Escape listeners over the same state race on document-listener attachment order'); StationInspector.tsx:113 (`{escape: false}` precedent); ColorField.tsx:158-180 (hand-rolled capture-phase + stopPropagation — the repo needed TWO mitigations for this exact hazard); plan §4:110, §9:226-229, §12 #23. Escape double-dismiss and outside-click dismissal both reproduced in probe harnesses against the real hook.

### B2. §5's safety argument is inverted: the `UndoSnapshot` type enforces nothing, R3 fears the wrong risk, and #13's annotation points the implementer at a test that cannot fail

**Why:** Three compounding errors on the plan's hardest change. (a) `UndoSnapshot = Omit<DocSnapshot,'name'>` is a structural SUPERTYPE of `DocSnapshot`. Verified by compiling against the repo's own tsc 5.9.3: passing a `DocSnapshot` variable to `pushHistory(s: UndoSnapshot)` compiles clean, exit 0 — excess-property checking never fires because every call site passes a variable, never a fresh literal. (b) R3 therefore has it backwards: it worries the change 'ripples into history.ts and any test that constructs a DocSnapshot' — grep proves that is exactly ONE file (history.test.ts) and it compiles unchanged. The real risk is a silently-accepted narrowing: land §5 items 1+3 but miss item 2 (beginHistoryGroup's capture at store.ts:1105) and `tsc -b` stays green while every grouped gesture pushes name-bearing snapshots onto pastStates forever. zundo's `undo()` does `userSet(nextState)` (index.js:15), so the stale name is dragged back. D6 silently fails on every drag, slider, and text-field edit. (c) The plan designates test #13 as the catcher ('This is the test that catches the pushHistory trap in §5; without the beginHistoryGroup change it fails'). I applied ONLY the zundo half to the real tree and ran both tests: #13 PASSED, #14 FAILED with `expected 'Untitled map' to be 'New'`. The annotation is exactly inverted. `moveStation` (store.ts:604) is a plain ungrouped `set`; `withRegionReconcile` (store.ts:1050-1057) never opens a group, so #13 never executes store.ts:1105 at all.

**Fix:** Three plan edits before step 2 begins. (1) Harden the type: `type UndoSnapshot = Omit<DocSnapshot,'name'> & { name?: never }` — verified to produce TS2345 on `pushHistory(docSnapshot)`, converting a silent runtime bug into a build failure. Costs nothing at legitimate call sites (pickUndoSnapshot and zundo's partialize both omit `name` entirely). (2) Rewrite R3: 'The pushHistory signature change ripples LESS than expected — a DocSnapshot is structurally assignable to Omit<DocSnapshot,"name">, so history.test.ts compiles unchanged. That is the hazard, not the relief: missing the store.ts:1105 capture leaves tsc green AND tests 12 and 13 green. #14 is the only guard.' (3) Move the parenthetical from #13 to #14, mark #14 non-droppable, and make it concrete rather than 'same assertion': `const g = beginHistoryGroup(); moveStation(id,120,90); g.commit(); setDocName('New'); undo();` → expect station reverted AND `name === 'New'`. The mutate inside the group must be a real doc change or commit's `docSnapshotsEqual` guard (store.ts:1131) returns early and #14 goes green for the wrong reason. Reword #13 as what it proves — the zundo partialize/equality half. Add to §13 step 2: land the zundo change, watch #12 and #13 go green and #14 stay RED, then fix beginHistoryGroup.

**Evidence:** store.ts:604 (`moveStation: (id,x,y) => set(withRegionReconcile(...))` — ungrouped), :939 (`setDocName` — ungrouped), :1000-1001 (zundo equality/partialize), :1050-1057 (withRegionReconcile never groups), :1105 (`const snapshot = pickDocSnapshot(...)`), :1133 (`pushHistory(snapshot)`); history.ts:13 (sole production caller is store.ts:1133); history.test.ts:7,11,18 (`let snap: DocSnapshot` → `pushHistory(snap)` — still compiles); node_modules/zundo/dist/index.js:15 (`userSet(nextState)`, no replace flag → shallow merge); plan §5:143-156, R3:328, §12:277-278. Both the tsc result and the #13-passes/#14-fails split were executed, not reasoned.

### B3. §3/§12 specify no IndexedDB isolation — test #2 fails on test #1's leftover, and the house-style fix deadlocks

**Why:** §12's tests 1-11 all write to one fixed DB (`massimo-library`, §2:59) with no reset specified anywhere; §4's only test-infra change is `import 'fake-indexeddb/auto'` in the global setup, which installs one IDBFactory per file and never resets it. Reproduced with real fake-indexeddb: run the plan's #1 then #2 and you get `[["Test Map",3]]` where #2 asserts `revisionCount === 2`. No name choice rescues it — if #1 used a different name, listMaps() returns 2 entries instead of 1. #3 and #10 inherit it. Then the obvious fix hangs: `indexedDB.deleteDatabase('massimo-library')` in a beforeEach fires `versionchange`, and with a module-level cached `IDBDatabase` and no `db.onversionchange`, the request goes to `blocked` and never fires `onsuccess` — reproduced, still pending at 2s. `npm run pre-pr` runs `test` before `build` and `e2e`, so the file dies on timeout and takes the gate with it. §3's nine-function API has no `closeDb()`, no `resetForTests()`, no injectable DB name — and never states connection lifetime. This is step 1 of §13, so it lands first. Note the repo has a unanimous convention the plan contradicts: ~8+ files reset storage in a file-local `beforeEach` (snapPrefs.test.ts:9, customPalettes.test.ts:5, viewportStore.test.ts:5, labelEditorPrefs.test.ts:8, saveLoad.test.tsx:321, App.keyboard.test.tsx:19, selection.test.ts:751, mirrorDispatch.test.ts:26), never in the global setup — so an implementer following house style walks straight into the deadlock.

**Fix:** Write the isolation strategy into §3 and §12 before step 1. Move the shim out of the global setup into `mapLibrary.test.ts` alone (this also closes R10), and use the no-production-hook variant: `beforeEach(async () => { const { IDBFactory } = await import('fake-indexeddb'); globalThis.indexedDB = new IDBFactory(); vi.resetModules(); lib = await import('./mapLibrary'); })` — a fresh factory plus a fresh module registry, so any cached connection dies with the module. Also state §3's connection lifetime explicitly (open-per-call, or cached with `db.onversionchange = () => { db.close(); cached = null; }`). Note the data leak is caused by the DATABASE persisting, not by connection caching — a per-call open+close still leaks the row — so the reset is required regardless of how connections are managed.

**Evidence:** src/test/setup.ts:1-31 (only teardown is `cleanup()`; no beforeEach, no storage reset); vitest.config.ts (setupFiles: ['./src/test/setup.ts'], no isolate override); plan §2:59, §3:80-95, §4:128, §12:262-273, R10:335. Both the data leak and the deleteDatabase `blocked` deadlock were reproduced with real fake-indexeddb in a gitignored probe.

## USER DECISIONS

1. D7: Clear is undoable TODAY — `onClear` (Toolbar.tsx:128-138) calls `clearAll()` and nothing else, and `clearAll` is an ordinary tracked `set` (store.ts:961), so Ctrl+Z after Clear restores the whole map right now (verified by probe: historyDepth increments, undo restores). D7 replaces that with a one-shot confirm dialog and `clearHistory()`. Net recovery is strictly worse — undo is recoverable forever; a dialog is a gate you click through once. The plan never discloses this trade (D7's note 'the existing file-load contract' is accurate about the file-load path, which genuinely does need clearHistory since undo must not cross into a replaced document — Clear doesn't, because the pre-Clear document is the same document). Still want D7?

2. D3 vs merging: a `renameMap` merge of two full maps forfeits 100 revisions to the 100/map cap — whether pruned at merge time (recommended) or at the next unrelated save (current spec). Do you want merges to be lossless (i.e. the cap is per-map-name and a merge may exceed it), or is losing the oldest 100 on merge the intended behavior?

3. Toast: the save confirmation is raised inside Toolbar's own `onSaveToLibrary`, where the dismissible `role="alert"` status span (`menuError`, Toolbar.tsx:79/:364-379) already lives and already serves export and parse failures. Widen `menuError` to `menuStatus: {kind:'error'|'info'}` and delete Toast.tsx + Toast.test.tsx (~85 LOC, one consumer), or do you specifically want a floating auto-dismissing toast as a distinct surface?

4. Suppressing the prompt is worse than the disease (it strands the common case). Do you want the ConfirmDialog to show what would move (count + latest-save timestamp or thumbnail) and default to 'Keep as separate map', or accept the ambiguity for now?
